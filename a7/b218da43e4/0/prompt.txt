## Findings

**1. `pageCache.ts` internals (`frontend/src/lib/pageCache.ts:1-86`)**
- `failed` map stores only `width` (highest failed width), not the `Error`/message — `.catch(() =&gt; { ...failed.set(k, width) })` (line 74) discards the error entirely.
- `isFailed()` (line 43-45) is exported, never called anywhere in the codebase (confirmed via grep — no matches for `isFailed` outside its own definition).
- `load()` (line 47-78): once `failed.get(k) &gt;= width`, it permanently no-ops for that width — `if (failedAt !== undefined &amp;&amp; failedAt &gt;= width) return` (line 56). There is **no manual-retry path**: calling `load()` again at the *same* width is silently ignored forever; only a request at a *strictly higher* width bypasses the guard. So a consumer wanting a "Retry" affordance can't just call `load()` again — pageCache would need a new function (e.g. `retry(path, page)` that deletes the `failed` entry) or `load` would need a `force` param.

<result># Implementation Plan: Surface `pageCache.ts` Render Failures in the UI

## 1. `pageCache.ts` changes

Change `failed` from `Map&lt;string, number&gt;` to a richer entry so the message survives, and add a minimal `retry` API instead of a `force` flag (keeps `load()`'s signature and all 8 existing call sites untouched).

```ts
interface FailedEntry { width: number; message: string }
const failed = new Map&lt;string, FailedEntry&gt;()

export function isFailed(path: string, page: number): boolean
export function getFailureMessage(path: string, page: number): string | undefined
export function retry(path: string, page: number): void
```

- `isFailed` keeps its exact current signature/behavior (existing callers, if any were added, don't break).
- `getFailureMessage(path, page)` returns `failed.get(pageKey(path,page))?.message`, used by the tooltip.
- `retry(path, page)`: deletes the `pageKey` entry from `failed` only (leave `loading`/`entries` untouched — there won't be a stale entry since a failed render never wrote to `entries`), then calls `notify()`. It deliberately does **not** call `load()` itself — the consumer's existing `useEffect` (which already re-runs `load()` on every relevant dependency change, or which the component re-triggers) is not guaranteed to re-fire just because `failed` changed. So `retry` must itself re-invoke the render: `retry(path, page, width)` — **the signature needs `width`** so it can call `load(path, page, width)` internally after clearing the flag. Revised:

```ts
export function retry(path: string, page: number, width: number): void {
  failed.delete(pageKey(path, page))
  load(path, page, width)
}
```

This is minimal surface area: one changed internal type, two new exports, `isFailed`'s signature untouched. In `.catch()`, capture `err instanceof Error ? err.message : String(err)` and store `{ width, message }` — replaces the current bare `.catch(() =&gt; {...})` with one that captures the error, satisfying the CLAUDE.md no-bare-catch rule.

## 2. `PageThumbnail.tsx` UX

Hover-tooltip only for v1 — no click-to-retry on the tiny thumbnail. Rationale: thumbnails are small, numerous, and virtualized; a systemic failure (missing `pdftoppm`) means retrying one-by-one is pointless — the user's real recovery path is fixing the environment and reloading the file, which already re-triggers `load()` on next scroll/mount. Adding a retry button here would also require new props/click-event plumbing (`stopPropagation`, since the wrapper's `onClick` selects the page) for marginal value.

In the placeholder div, add a third branch:

```tsx
&lt;div className={styles.placeholder} style={{ height: thumbHeight }}&gt;
  {pageCache.isLoading(pdfPath, page) &amp;&amp; &lt;Loader size="xs" /&gt;}
  {!pageCache.isLoading(pdfPath, page) &amp;&amp; pageCache.isFailed(pdfPath, page) &amp;&amp; (
    &lt;Tooltip label={pageCache.getFailureMessage(pdfPath, page) ?? 'Failed to render page'} openDelay={500}&gt;
      &lt;IconPhotoOff size={16} color="var(--mantine-color-red-6)" /&gt;
    &lt;/Tooltip&gt;
  )}
&lt;/div&gt;
```

`IconPhotoOff` over `IconAlertTriangle` — it's already semantically "image failed to load," reserving the triangle/yellow for warnings (page-count mismatch, corrupt-file badge) elsewhere in the app, keeping icon vocabulary consistent (error=red/photo-off, warning=yellow/triangle). Needs the `Tooltip` import from `@mantine/core` and `IconPhotoOff` from `@tabler/icons-react` (both new imports to this file).
