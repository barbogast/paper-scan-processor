**1. `cancelledRef` + post-loop idle sweep can be replaced by "cancel = clear the pending queue now"**
- File: `frontend/src/components/DriveUploadMode/useUploadQueue.ts`, lines 46, 61, 75–78, 95–97 (and the `cancelledRef.current = false` reset at line 102)
- Summary: Cancellation is modeled as a flag the worker polls, plus a deferred cleanup pass, when the same behavior is one synchronous operation.
- Cost: Four pieces of machinery — the `cancelledRef`, the `!cancelledRef.current` loop condition, the post-loop sweep that returns never-attempted tasks to idle, and flag resets in two places (`run` and `reset`) — plus the `runningRef` guard in `cancelRemaining` that exists only because a stray `cancelledRef = true` would poison the *next* run.
- Simpler form: `cancelRemaining` marks every task still in `queueRef.current` idle and empties the array immediately. The in-flight upload is untouched (it was already shifted out); when it settles, the loop condition `queueRef.current.length &gt; 0` is false and the run winds down naturally. This deletes `cancelledRef` entirely, the loop condition clause, the post-loop sweep, both flag resets, and the guard in `cancelRemaining` — and as a bonus, queued files flip to idle at cancel time instead of after the in-flight upload finishes. All existing tests still pass conceptually (the idle assertions are only checked after the in-flight settle anyway). It also removes a latent oddity in the current form: tasks enqueued between cancel and the in-flight settle get silently swept to idle by the flag-based version.

**2. `statusesRef` mirrors `statuses` state, but its only read is derivable from the queue itself**
- File: `frontend/src/components/DriveUploadMode/useUploadQueue.ts`, lines 43, 51–54, 84–87
- Summary: A full mirrored Map (ref + state kept in lockstep by `setStatus`) exists solely so `enqueue`'s dedup filter can read fresh state, but "queued or uploading" is exactly "still in the queue" if the worker peeks instead of shifting.
- Cost: Two sources of truth for the entire status map, a custom `setStatus` that must be used for every write to keep them in sync, and a dedup check routed through status strings when the queue already holds the answer.
- Simpler form: Have the worker peek (`const task = queueRef.current[0]`) and shift only after the upload settles (after the generation guard). ## Efficiency findings

**1. `enqueue` and the post-cancel drain do one full Map copy + one setState per task — O(N²) copying where one batched copy would do**
- File: `frontend/src/components/DriveUploadMode/useUploadQueue.ts`, lines 83–90 (`enqueue`) and 75–76 (post-cancel idle drain), via `setStatus` at lines 51–54.
- Cost: `setStatus` does `new Map(statusesRef.current)` per call. Enqueueing N files runs it N times synchronously, copying maps of size 1..N — O(N²) entry copies plus N `setStatuses` calls in one tick (React batches the renders, but the allocations and copies all happen). Same shape in the cancel drain loop. At the stated scale (hundreds of files) this is a few ms, so it's a pattern flag more than a hot spot — but it's the one quadratic loop in the diff and grows fast past that scale.
- Cheaper alternative: batch the loop into a single copy — `const next = new Map(statusesRef.current); for (const t of fresh) next.set(t.path, {state:'queued'}); statusesRef.current = next; setStatuses(next)`. Same for the idle drain. Keep per-file `setStatus` inside the worker loop as-is; there it's one copy per network upload, which is fine.

**2. `statusOf` allocates a fresh `{ state: 'idle' }` on every miss**
- File: `frontend/src/components/DriveUploadMode/useUploadQueue.ts`, lines 109–112.
- Cost: before anything is enqueued, every file row's status lookup is a miss, so a render of a few hundred rows allocates a few hundred identical objects — and each call returns a new identity, so any downstream `memo`/equality check on the status always sees a change even when nothing did (extra re-renders are the real cost, not the allocation).
- Cheaper alternative: a module-level `const IDLE: UploadStatus = { state: 'idle' }` (optionally `Object.freeze`d) returned for misses; stable identity makes memoized consumers actually skip.

**3. `flattenFiles` allocates intermediate arrays per tree level — fine for the worker, watch the advertised per-render rollup use**
- File: `frontend/src/components/DriveUploadMode/useFileTree.ts`, lines 22–24.
- Cost: `[...group.files, ...group.subgroups.flatMap(flattenFiles)]` copies every file O(depth) times through intermediate arrays. For a single call at dozens-to-hundreds of files this is negligible — no change needed for the enqueue path. But the doc comment commits future callers to using it for "per-group status rollups" on render: calling `flattenFiles(group)` for every group node each render re-walks each subtree once per ancestor, multiplying the work by tree size × depth on every status tick (and there are two ticks per uploaded file).
- Cheaper alternative when that caller lands: either an accumulator variant (`function collect(g, out)` pushing into one array) plus `useMemo` of the flattened list per group keyed on the tree (the tree is immutable between scans, so it memoizes cleanly), or compute rollups in one bottom-up pass instead of flatten-per-group.

**Not flagged / pre-existing note:** each `UploadFile` RPC re-reads and re-parses `credentials.json` and the token file and rebuilds the `*drive.Service` (`service()` in `/Users/ben/git/paper-scan-processor/backend/drive/auth.go:68`, called from `upload.go:20`). The new queue makes this per-file, but the diff didn't introduce the pattern (it predates the `name` param change, and all Drive RPCs share it), refreshed tokens are persisted so there's no repeated token-endpoint round trip, and a couple of small local file reads are noise next to a network upload. Only worth caching the service if profiling ever says otherwise.

The sequential one-at-a-time worker was not flagged per instructions (deliberate spec choice). The Go changes (`app.go`, `upload.go`) introduce no wasted work. Overall the diff is close to clean; findings 1–2 are cheap, contained fixes and finding 3 is a forward-looking caution tied to the module's own doc comment.</result>
